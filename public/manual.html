QFI Financial Engine — Full Equation Set

The QFI (Qabban Financial Intelligence) engine converts raw green-bean cost into tier-based wholesale prices using the Sponge baseline coefficient and a gross-margin formula.

── Step 1: True Roasted Cost ───────────────────────────────────── // Converts green-bean purchase price to roasted cost per kg. // Dividing by 0.82 accounts for the 18% mass lost during roasting. trueRoastedCost = costPerKgGreen ÷ SPONGE_BASELINE_COEFFICIENT = costPerKgGreen ÷ 0.82 Example: SAR 100/kg green → SAR 121.95/kg roasted ── Step 2: Wholesale Price (Gross-Margin Formula) ──────────────── // Gross margin = profit as % of selling price (not markup on cost). // Formula: price = cost ÷ (1 − margin) wholesalePrice = trueRoastedCost ÷ (1 − targetMargin) Tier prices for SAR 100/kg green cost: wpBronze = (100 ÷ 0.82) ÷ (1 − 0.40) = 121.95 ÷ 0.60 = SAR 203.25 / kg wpSilver = (100 ÷ 0.82) ÷ (1 − 0.35) = 121.95 ÷ 0.65 = SAR 187.62 / kg wpGold = (100 ÷ 0.82) ÷ (1 − 0.28) = 121.95 ÷ 0.72 = SAR 169.38 / kg ── Step 3: Live Inventory Value ────────────────────────────────── liveInventoryValue = wholesalePrice × liveRoastedKg ── Step 4: Projected Profit ────────────────────────────────────── projectedProfit = (wholesalePrice − trueRoastedCost) × liveRoastedKg ── Step 5: Environmental P&L (Sponge Impact) ───────────────────── spongeKgDelta = (spongeCoeff − 0.82) × liveGreenKg environmentalPnL = spongeKgDelta × wholesalePrice
Why gross-margin, not markup? A 40% gross margin means 40% of the selling price is profit — this is the standard retail/wholesale pricing convention. A 40% markup on cost would be cost × 1.40, which yields a lower gross margin of ~28.6%. Qabban uses gross-margin convention throughout.

Hybrid Discount Engine — Full Equation Set

The final price a cafe pays is the wholesale price reduced by two stacking discounts: a loyalty tier base discount and an optional bulk volume bonus. Both are additive (not compounding).

── Inputs ──────────────────────────────────────────────────────── lifetimeKg = total kg purchased by this cafe across all time orderKg = kg in the current order BAG_SIZE_KG = 60 kg (standard sack size) BULK_THRESHOLD = 10 bags (strictly greater than) ── Step 1: Determine Tier ──────────────────────────────────────── tier = Gold if lifetimeKg ≥ 2001 kg = Silver if lifetimeKg ≥ 501 kg = Bronze otherwise tierBaseDiscount = 0% (Bronze) = 3% (Silver) = 5% (Gold) ── Step 2: Bulk Bonus ──────────────────────────────────────────── bags = orderKg ÷ 60 isBulk = bags > 10 // 600 kg exactly does NOT qualify — must exceed bulkBonus = 10% if isBulk = 0% otherwise ── Step 3: Total Discount (additive stacking) ─────────────────── totalDiscountPct = tierBaseDiscount + bulkBonus totalDiscountFraction = totalDiscountPct ÷ 100 ── Step 4: Final Price ─────────────────────────────────────────── discountedPricePerKg = wholesalePrice × (1 − totalDiscountFraction) orderTotal = discountedPricePerKg × orderKg ── Examples ────────────────────────────────────────────────────── Gold + 750 kg order (12.5 bags): 5% + 10% = 15% off SAR 169.38 × (1 − 0.15) = SAR 143.97/kg Silver + 300 kg order (5 bags): 3% + 0% = 3% off SAR 187.62 × (1 − 0.03) = SAR 181.99/kg Bronze + 660 kg order (11 bags): 0% + 10% = 10% off SAR 203.25 × (1 − 0.10) = SAR 182.93/kg

21 Sponge Effect — Dynamic Yield Engine
Coffee beans are hygroscopic — they absorb or lose moisture based on ambient humidity. The Sponge Effect Engine dynamically adjusts the standard 0.82 roasting yield coefficient based on real warehouse humidity, producing more accurate inventory weights and a true Environmental P&L figure.
The Baseline — Standard Roast Shrinkage

During roasting, green coffee beans lose approximately 18% of their mass through evaporation of moisture and CO₂ off-gassing. This gives the standard yield coefficient:

SPONGE_BASELINE_COEFFICIENT = 0.82 roastedKg (baseline) = greenKg × 0.82 Example: 100 kg green → 82 kg roasted (18 kg lost to roasting)
Piecewise Humidity Rules

The baseline coefficient is adjusted based on the active relative humidity (RH%) at the storage branch. There are two adjustment rules and one baseline band:

RuleConditionDelta (Δ)CoefficientPhysical Explanation
Rule A
Moisture Absorption		 RH > 70% +0.005 0.825 High humidity → beans absorb ambient moisture before roasting → heavier → less % mass lost → more roasted output per green kg
Baseline
Normal Band		 20% ≤ RH ≤ 70% 0 0.820 Standard storage conditions — 18% shrinkage applies
Rule B
Evaporation Loss		 RH < 20% −0.003 0.817 Very dry conditions → beans lose pre-roast moisture → lighter before roasting → greater % mass lost → less roasted output
Full Equation Set
── Coefficient Calculation ────────────────────────────────────── spongeCoeff = 0.82 + Δ where Δ = +0.005 if RH > 70% (Rule A) = 0 if 20% ≤ RH ≤ 70% (Baseline) = −0.003 if RH < 20% (Rule B) ── Roasted Weight (Sponge-adjusted) ──────────────────────────── roastedKg = greenKg × spongeCoeff Rule A example (RH = 75%): 100 kg × 0.825 = 82.5 kg (+0.5 kg vs baseline) Baseline (RH = 50%): 100 kg × 0.820 = 82.0 kg Rule B example (RH = 15%): 100 kg × 0.817 = 81.7 kg (−0.3 kg vs baseline) ── Sponge Delta (kg gained or lost vs baseline) ───────────────── spongeKgDelta = (spongeCoeff − 0.82) × greenKg = Δ × greenKg Rule A: +0.005 × 100 = +0.5 kg gain Rule B: −0.003 × 100 = −0.3 kg loss ── Environmental P&L (SAR impact of sponge delta) ─────────────── environmentalPnL = spongeKgDelta × wholesalePrice Positive PnL = moisture gain → more saleable weight → revenue upside Negative PnL = evaporation loss → less saleable weight → revenue shortfall Example (Gold tier, wpGold = SAR 169.38/kg, RH = 75%, green = 100 kg): environmentalPnL = +0.5 × 169.38 = +SAR 84.69 ── ZATCA Shrinkage Report Rows ────────────────────────────────── baselineRoastedKg = greenKg × 0.82 actualRoastedKg = greenKg × spongeCoeff spongeAdjKg = actualRoastedKg − baselineRoastedKg ruleASurplusKg = max(0, spongeAdjKg) // only Rule A gains ruleBDeficitKg = min(0, spongeAdjKg) // only Rule B losses
Hybrid Humidity Source — How RH is Resolved

Each branch has two possible humidity sources. The engine selects the most reliable one automatically:

PrioritySourceCondition to UseFallback?
1 — Primary IoT Sensor (ESP32/DHT22) Branch humidity_source = IOT_SENSOR AND last reading < 60 minutes old —
2 — Fallback Weather API No IoT data, source = WEATHER_API, or IoT reading is stale (> 60 min) Always available

When a stale IoT reading is used as fallback, the system flags the response with isStale: true so admins can see the data quality in the branch card.

22 ZATCA Phase-2 Compliance
QABBAN OS generates fully compliant ZATCA Phase-2 UBL XML e-invoices with 15% VAT, QR codes, and a Bulk Shrinkage Report for Saudi tax authority submission.
Landed Price — Full Equation Set

The Landed Price Calculator converts a vendor's origin FOB price into the final SAR per kg cost to the Saudi buyer, including all fees and VAT:

── Constants ───────────────────────────────────────────────────── SAUDI_CUSTOMS_RATE = 5% (ad valorem on CIF value) QABBAN_PLATFORM_FEE = 1.5% (of CIF) ZATCA_VAT_RATE = 15% shippingEstimate = SAR 1,500 (flat base estimate) ── Step 1: FOB value in SAR ────────────────────────────────────── fobPriceSar = fobPriceUsd × effectiveRate fobTotalSar = fobPriceSar × quantityKg ── Step 2: CIF (Cost, Insurance, Freight) ─────────────────────── cif = fobTotalSar + shippingEstimate ── Step 3: Customs & Fees ──────────────────────────────────────── customsFees = cif × 0.05 qabbanFee = cif × 0.015 ── Step 4: VAT Base & VAT ──────────────────────────────────────── vatBase = cif + customsFees + qabbanFee vat = vatBase × 0.15 ── Step 5: Final Landed Price ──────────────────────────────────── landedPriceSar = fobTotalSar + shippingEstimate + customsFees + qabbanFee + vat landedPricePerKg = landedPriceSar ÷ quantityKg ── Example: 100 kg lot, USD 4.20/kg, effectiveRate 3.825 ────────── fobTotalSar = 4.20 × 3.825 × 100 = SAR 1,606.50 cif = 1,606.50 + 1,500 = SAR 3,106.50 customsFees = 3,106.50 × 0.05 = SAR 155.33 qabbanFee = 3,106.50 × 0.015 = SAR 46.60 vatBase = 3,106.50 + 155.33 + 46.60 = SAR 3,308.43 vat = 3,308.43 × 0.15 = SAR 496.26 landedTotal = 1,606.50+1,500+155.33+46.60+496.26 = SAR 3,804.69 landedPerKg = 3,804.69 ÷ 100 = SAR 38.05/kg
Invoice VAT Calculation
── ZATCA Invoice Lines ─────────────────────────────────────────── subtotal = unitPriceSar × quantityKg vatAmt = subtotal × ZATCA_VAT_RATE (= subtotal × 0.15) total = subtotal + vatAmt Example: SAR 169.38/kg × 100 kg subtotal = SAR 16,938.00 vatAmt = 16,938.00 × 0.15 = SAR 2,540.70 total = SAR 19,478.70

Bulk Shrinkage Report — What It Covers

The ZATCA Bulk Shrinkage Report documents the difference between the standard 18% roast loss and the actual sponge-adjusted loss across all lots in a 30-day period. This supports tax authority documentation of inventory mass changes.

Per lot, the report records: baselineShrinkKg = greenKg × 0.18 // standard expected loss spongeAdjKg = (spongeCoeff − 0.82) × greenKg // surplus or deficit ruleASurplusKg = max(0, spongeAdjKg) ruleBDeficitKg = min(0, spongeAdjKg) 30-day totals are summed across all lots and exported as CSV.
GET /admin/finance/zatca-export → Downloads qabban-zatca-bulk-shrinkage-{date}.csv
Covers 30-day period · Standard 18% baseline · Sponge coefficient per branch · 15% ZATCA VAT

Reconciliation Equation Set

The reconciliation engine compares what Foodics says was sold (theoretical usage) against what the Acaia scale actually measured being used (actual usage), then converts any gap into a SAR financial figure.

── Step 1: Theoretical Usage (from Foodics POS) ───────────────── // For each Foodics order, look up the drink name in PULSE_BEAN_MAP // and sum the grams across all items. theoreticalUsageGrams = Σ (PULSE_BEAN_MAP[drinkName] × quantity) for each item in all Foodics orders of the day Example: 10 Espressos (18g) + 5 Double Lattes (36g) = 180 + 180 = 360g ── Step 2: Actual Usage (from Acaia Scale) ─────────────────────── // Sum all WasteLog entries for this branch/session/date. // Each entry is a scale reading rounded to 1 decimal place. actualUsageGrams = Σ wasteLogs[i].weightGrams (filtered by branchId + date + optional sessionId) ── Step 3: Variance ────────────────────────────────────────────── varianceGrams = actualUsageGrams − theoreticalUsageGrams Positive variance → actual > theoretical → over-use (waste or theft risk) Negative variance → actual < theoretical → under-use (possible POS miss) ── Step 4: Financial Loss ──────────────────────────────────────── // Only positive variance (over-use) generates a loss. // costPerKgSar comes from the branch's active lot (OPTIMAL or MONITOR status). financialLossSar = 0 if variance ≤ 0 = (varianceGrams ÷ 1000) × costPerKgSar if variance > 0 Example: variance = +45g · cost = SAR 180/kg financialLossSar = (45 ÷ 1000) × 180 = SAR 8.10 ── Step 5: Foodics Inventory Adjustment (optional) ────────────── // If pushAdjustment = true, POST to Foodics /inventory_transactions: adjustmentKg = |varianceGrams| ÷ 1000 adjustmentType = "waste"

34 Risk Watchdog — Sustained Humidity Violation Engine
Route: /admin/watchdog — Automated 6-hour cron engine that scans every lot's Climate Passport for sustained high-humidity exposure. Escalates violations to CRITICAL, notifies the branch manager via WhatsApp, flags the lot in the Inventory tab, and injects an urgent red banner on the Admin Dashboard.
What the Watchdog Monitors
Trigger Condition: A lot is flagged when every Climate Passport reading in the past 48 hours shows Relative Humidity above 70% RH. A single below-threshold reading resets the window — spikes are not flagged, only sustained exposure.
Violation Thresholds
ParameterValueNotes
Humidity Threshold> 70% RHAll readings in window must exceed this
Observation Window48 hoursLookback period from current time
Minimum Readings≥ 2At least 2 data points required to flag
Cron IntervalEvery 6 hours0 */6 * * * Cloudflare Cron Trigger
Safe Storage Target< 50% RHAction instruction sent to branch manager
Detection Logic — Step by Step
  • Every 6 hours the checkHumidityViolations() function runs automatically via Cloudflare Cron Trigger
  • For each lot, only Climate Passport log entries within the last 48 hours are considered
  • If the window has ≥ 2 readings and every single one exceeds 70% RH, the lot is a confirmed violation
  • Lots already flagged CRITICAL with an existing UNREAD system notification are skipped (no duplicate alerts)
  • Violations are persisted via persistViolations() — lot status updated, notification inserted, WhatsApp queued
  • WhatsApp batch is dispatched asynchronously using ctx.waitUntil() so the cron does not block on delivery

Plan Selection Modal · Hosted Checkout · Webhook Auto-Unlock

The upgrade flow is a fully self-contained in-app checkout that never redirects users to an internal management portal. It uses a Netflix-style dark modal for plan selection, then hands off to Moyasar's Hosted Checkout page for payment.

applyPlanUpgrade Logic

The shared helper applyPlanUpgrade(branchId, product) is called by both the webhook and dev-capture endpoints:

  • ERP_PRO: Sets plan_type = 'ERP_PRO' and subscription_expires_at = 31 days from now.
  • PULSE: Sets pulse_enabled = true. If branch is still FREE, auto-upgrades to ERP_PRO first.
